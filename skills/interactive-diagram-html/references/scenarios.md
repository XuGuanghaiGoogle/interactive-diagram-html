## 1. 系统 / 环境构成图

**布局**：容器型。以左→右的数据方向排列容器。起点参考 `assets/examples/system-architecture.json`。

**推荐分组**：外部（来源 / 利用者）｜边界（DNS、CDN、WAF、认证）｜网络（VPC / VNet、子网）｜应用层｜数据层｜托管服务｜运维与 CI/CD。云平台之间的责任分界（例如 Databricks 控制平面和客户云账号）要各自成框。

**节点类别**：按服务种类划分，例如外部、网络、计算、存储、数据库、安全、AI、集成、运维。有官方配色的平台沿用其色系（AWS 橙、Azure 蓝、Databricks 红）。

**连线**：数据流或调用关系。虚线表示可选、异步或回流。

**阶段**：M0 / PoC 用「必須 / 簡略 / 対象外」三档，`dim: ["対象外"]`。每个节点的 `phase.text` 写 M0 下的具体构成，例如「1 台、Single-AZ、自動停止 10 分」。

**面板**：role 写这个服务负责什么；fn 写配置方针，比如规格、冗余、权限、加密；io 写连接对象；rel 写与处理流程图中哪个逻辑组件对应。

**表格**：① `phase` 表（M0 构成要件）；② `custom` 表（逻辑组件 → 实现服务的对应，或者与另一云平台的对应）。

**卡片**：M0 目的与前提（期间、范围、合格标准、M0 也不省略的项目、M0 割舍的项目）｜成本概算（写量级并注明需要复核）｜网络与接入路径｜安全。

**第二轮问题**：
- 使用哪个平台或哪家云？是否已有账号、租户和身份提供方？
- 是否要区分 PoC 与正式环境？PoC 的期间和规模大约是多少？
- 是否需要成本概算？
- 有没有必须遵守的限制（闭域网络、数据所在地、现有监控工具）？

## 2. 处理流程图

**布局**：带状型。纵向堆叠几条横向泳道，每条泳道内按从左到右的顺序排列步骤：① 采集 / 录入｜② 存储｜③ 提供 / 处理｜④ 共通功能（模型、平台功能）。

**节点**：步骤用 `rect`，判断用 `diamond`，存储用 `cylinder`（设置 `dot` 颜色），异常或通知用红色系类别，补充说明用 `note`。

**连线**：处理顺序。判断分支的连线上写「はい / いいえ」「合格 / 不合格」等标签。回流、删除传播之类用虚线。

**关联**：处理节点的 `uses` 写它用到的存储节点，右下角会显示对应颜色的圆点；`tags` 写它用到的模型或平台功能的缩写，配合 `tagLegend` 使用。

**面板**：fn 写处理细则；如果是审查或判断类步骤，写清输入、输出、判定方法、失败时的处理方针和需要记录的审计项目。

**表格**：① `uses` 表（处理 × 存储矩阵）；② 需要时加 `phase` 表。

**卡片**：各泳道的要点（编号列表）｜设计原则，比如职责单一、权限只在一处判定、保留原件不改。

**第二轮问题**：
- 流程的起点和终点分别是什么？
- 有哪些异常分支、审查或审批？
- 用到哪些存储？有没有队列、缓存或审计日志？
- 需要"处理 × 存储"对应表吗？

## 3. 开发计划

**布局**：时间轴型。横轴是周或 Sprint（`timeline`），纵向泳道是工作流。起点参考 `assets/examples/dev-plan.json`。

**推荐泳道**：里程碑｜基础与环境｜功能开发（按功能域拆成 2～3 条）｜外部对接｜测试｜迁移与发布。

**节点**：功能或任务用 `rect`，横跨多个 Sprint 时，宽度按列数计算；里程碑用 `diamond`，放在 Sprint 的交界线上。类别可以分为新规、改修、基础、对接、测试、迁移、里程碑。`tags` 写负责团队，配合 `tagLegend` 使用。

**连线**：依赖关系，从前置任务指向后续任务，不能逆着时间方向画。关键路径用 `bold`，外部依赖或弱依赖用 `dash`。

**阶段**：P0（首次发布必须）/ P1 / P2，`dim: ["P1","P2"]`，打开开关后只剩首次发布的范围。

**面板**：建议设置 `panelLabels` 为 `{ "role": "目的", "fn": "機能説明", "io": "入出力・区分", "rel": "備考" }`。
- `kv`：担当 / 工数（人日）/ 期间 / 依存
- `role`：为什么要做
- `fn`：功能说明，4～6 条
- `sections`：`受入基準`，写可以验证的完成条件，例如「10 万件を 2 秒以内に検索」
- `io`：画面、API 或批处理的区分，以及输入和输出
- `phase.text`：P0 做到哪一步，哪些留到 P1

**表格**：① `phase` 表（发布范围）；② `custom` 表（功能一览：ID / 名称 / 区分 / 范围 / 期间 / 工数 / 担当）；③ `custom` 表（里程碑：日期 / 名称 / 判定标准 / 负责人）。

**卡片**：目的与范围｜前提条件｜体制与分工｜工数汇总（按阶段合计，另留缓冲）｜主要风险与对策｜P0 不省略的项目和割舍的项目。

**第二轮问题**：
- 期间和节奏：从哪天到哪天，按周还是按 Sprint，一个 Sprint 几周？
- 功能列表从哪里来（需求文档、积压任务、会议记录）？
- 团队构成与人数？是否有固定的里程碑日期（评审、测试开始、发布）？
- 首次发布的范围是否已经确定？

## 4. 业务流程（泳道）

**布局**：泳道型。每条横向泳道代表一个角色或部门，从左到右按步骤推进；按业务阶段划分列时，可以用 `timeline` 画列头。

**节点**：业务步骤用 `rect`，判断用 `diamond`，使用的系统或文件用 `cylinder` 或 `note`。跨泳道的交接必须画连线，因为交接处最容易出问题，也是评审最关心的地方。

**面板**：
- `kv`：担当 / 所需时间 / 频率 / 使用系统
- `fn`：作业内容
- `sections`：写「判断標準」「例外処理」
- `io`：输入和输出的单据或数据

**表格**：`custom` 表（步骤一览：No / 步骤 / 担当 / 输入 / 输出 / 系统 / 所需时间），可以另加 `custom` 表列出课题（现状问题 → 改善方案）。

**卡片**：对象业务与范围｜现状课题｜改善后的变化｜规则与例外。

**第二轮问题**：
- 涉及哪些角色或部门？
- 流程由什么触发、在哪里结束？
- 有哪些例外处理和审批？
- 用到哪些系统或单据？这次画的是现状（As-Is）还是目标（To-Be）？

## 5. 组织 / 体制图

**布局**：自上而下的树形。每一层用同一个 y 坐标，汇报线用 `b→t` 连接。团队可以用 `groups` 包起来。

**节点**：角色或团队用 `rect`，外部组织用虚线类别，兼任的情况写在 `tags` 里。

**面板**：
- `kv`：人数 / 负责人 / 汇报对象 / 会议体
- `role`：使命
- `fn`：职责
- `sections`：写「権限」「成果物」

**表格**：`custom` 表，做成 RACI 或角色一览。

**卡片**：体制的目的｜会议体与节奏｜升级（エスカレーション）路径。

**第二轮问题**：
- 顶层是谁？分几层？
- 是否包括外部公司或供应商？
- 需要 RACI 吗？如果需要，要覆盖哪些工作项？

## 6. 其他场景

路线图、迁移计划、API 构成、安全边界图等场景，先从上面挑一个最接近的布局类型：

- 有时间顺序：用时间轴型（参照开发计划）
- 描述"谁在哪里、连接到哪里"：用容器型（参照构成图）
- 描述"先做什么、再做什么"：用带状型（参照处理流程图）
- 描述"谁向谁汇报"：用树形（参照体制图）

然后问清楚三件事：分组是什么、节点是什么、连线表示什么。
